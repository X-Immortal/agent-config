# 持久化文字的命名与表达规范

## 一、目标和适用范围

本 Skill 用于提高软件工程**持久化文字产出**的可理解性和可追溯性，使这些内容在离开当前对话后，仍能由团队成员、未来的维护者或其他 Agent 准确阅读与使用。

核心要求：**使用具体动作、具体对象和可核验事实描述工作；不要让模糊代号、比喻、口号或未经说明的结论代替信息。**

### 1.1 适用内容

- Git commit message（主题与正文）、PR 标题、PR 描述、代码审查记录。
- `README.md`、`docs/**/*.md`、`CHANGELOG.md`、设计说明、决策记录、实验报告、故障排查记录和测试报告。
- `AGENTS.md`、`SKILL.md`、项目工作日志、上下文压缩前的交接记录、供其他 Agent 恢复任务的持久化材料。
- 脚本、Git Hook、CI 配置或工具源文件中，准备长期保留的面向用户的诊断消息和错误提示。
- 代码注释、用户可见的程序文案等确实属于当前写入目标的自然语言文本。

凡是要为长期记录中的操作、问题、测试、验证、现象、方案或结论命名，均应按该标准检查。

### 1.2 不适用内容

- 一般的 Agent 对话、即时状态回复或不准备保存的临时讨论；这些由会话层规范处理。
- 仅修改程序逻辑、且没有新增或改写持久化自然语言内容的任务。
- 无需修改的第三方原文、日志、协议字段、错误码及其他必须精确保留的标识符。

### 1.3 执行方式

1. 明确当前真正要创建、修改或审查的持久化文本，以及其读者和用途。
2. 起草前确认事实、项目现有术语和编号约定；必要时查看相关上下文。
3. 起草时使用本 Skill 中的命名、措辞、编号和证据要求。
4. 提交或保存前，对**实际修改的文本**进行一次针对性检查，并直接修正不清晰的表达。
5. 不额外创建审计报告、术语表、登记簿或其他辅助文件，除非任务或项目规范本来要求。

## 二、命名必须自解释

### 2.1 具体动词、对象与结果

给操作、问题、测试、方案或文档条目命名时，优先选用以下结构：

- **具体动词 + 具体对象**：`验证登录接口的令牌刷新行为`。
- **对象 + 具体状态或事实**：`TL-7DR7230 LED 配置问题`。
- **动作 + 条件 + 结果**：`无效令牌请求被拒绝，接口返回 401`。

名称应当让不了解当前对话的读者判断指向什么；标题不必因此写成过长句子。

| 不合格名称 | 更明确的名称 | 问题 |
| --- | --- | --- |
| `L1 问题` | `TL-7DR7230 LED 配置问题` | 只有代号，没有对象。 |
| `阶段 A 存档` | `上下文压缩前备份` | 依赖不透明的阶段定义。 |
| `修复问题` | `修复令牌过期后刷新失败的问题` | 缺少修复对象。 |
| `测试 3` / `T3` | `验证 3：检查无效令牌的接口响应` | 编号替代了内容。 |
| `方案 B` | `方案 B：使用 Git worktree 隔离并行开发` | 不说明方案含义。 |
| `完成适配` | `将工具调用参数适配为当前 API 要求的格式` | 没有明确改变的内容。 |

不为普通工作项创造没有必要的“字母 + 数字”代号；如果需要编号，编号旁必须包含具体内容。

## 三、序号、代号与可追溯性

### 3.1 序号不是名称

`T1`～`T5`、`S1`/`S2`、`E1`/`E2` 等标记只表达顺序或类别，不能单独充当验证或实验的名称。跨文档引用时尤其容易失去语义。

优先使用：

- `验证 1：检查客户端工具列表是否保持不变`
- `验证 2：确认服务端没有额外注入工具`
- `对照 1：比较调整前后的工具调用响应`

对于已有的正式测试编号、Issue 编号或外部规范编号，可以保留，但在关键位置补上可理解的标题。

### 3.2 序号条目要包含实际信息

推荐结构：**序号 + 具体动作或事件 + 必要条件、判断与结果**。

不合格：

> 2. tools 剥离。

合格：

> 2. tools 剥离验证通过（首次 400 暴露 alpha 协议扁平 tools 格式；修改后回显仅包含客户端工具，没有服务端注入）。

上述表述应以实际获得的响应或日志为依据。没有执行相应验证时，不得照搬“验证通过”。

待办也要写明目标，例如“补充无效令牌的回归测试”，不要只写“测试补充”。

### 3.3 新编号的定义与登记

1. 先判断是否需要代号；自然语言名称足够清楚时，不额外建立缩写体系。
2. 若代号需要长期跨文件使用，首次出现时写明含义、用途和适用范围。
3. 仓库已有统一术语表或编号登记位置时，在该**单一权威位置**维护新定义，其他文档引用它。
4. 仓库没有登记机制时，直接在首次出现处定义即可；不为了临时编号创造新的管理体系。
5. 已有协议名称、测试 ID、Issue 编号、commit hash、错误码和外部约定标识符不得擅自改写。

## 四、使用平实中文描述动作、事实和结论

### 4.1 保留必要信息

重要记录根据实际需要交代：

- **动作**：执行了什么或改变了什么。
- **对象**：涉及的文件、模块、接口、测试或配置。
- **原因**：为什么这样做；当原因影响理解时说明。
- **范围**：实际覆盖哪些条件、文件或用例。
- **结果**：获得哪些观察结果，哪些尚未验证。

不合格：

> 登录搞定，测试跑通，后续再收口。

合格：

> 已修改登录接口的令牌校验逻辑。执行了登录成功和无效令牌两项测试，结果均符合预期；尚未执行令牌过期后的自动刷新测试。

不必机械填满五个字段，只需保证记录独立可读。

### 4.2 区分证据强度

- 代码已修改，不自动意味着行为已经验证。
- 某项测试通过，不自动意味着所有相关条件都已覆盖。
- 用户判断、作者推测、计划中的改动和实际观察结果应有明确区分。
- 不能为了让记录显得完整而编造测试、错误原因或修复结论。

避免单独使用“彻底解决”“全部 OK”“完全闭合”“肯定没问题”等口号式表述。有证据时具体说明，无证据时标明未验证范围。

### 4.3 长期文档的排版风格

- 使用常规 Markdown 标题、列表、表格和必要标点。
- 不用 emoji、勾叉图标或装饰性特殊符号代替“通过”“失败”“待检查”等状态文字。
- 不使用 `§` 等不必要的特殊符号进行标题编号。
- 保留代码、路径、命令、日志、协议字段和必须精确使用的字符；不得为了排版风格破坏技术内容。
- 如果项目或用户明确要求特定格式，遵从既有格式。

## 五、专业术语与含糊表达

### 5.1 判断标准

平实中文使用意思完整、字面可理解的句子。专业术语具有在相关领域内可查证的定义；它的专业性来自意义准确，不来自听起来复杂。

例如“事务”“回滚”“死锁”“竞态条件”“幂等性”，或审计领域的“穿行测试”“期后事项”，在对应语境中都可以准确使用。

应警惕三种表达：

1. **跨领域借喻**：把别的领域的词用于工程动作，但没有说明对应操作。
2. **口语或网络用语**：离开当前聊天后，含义不稳定。
3. **夸张程度词或抽象管理表达**：强调情绪和评价，却不交代动作、对象、范围与结果。

### 5.2 常见词语的精确改写

| 含糊表达 | 按实际语义选择的改写 | 检查重点 |
| --- | --- | --- |
| `钉死` | `当次实测确认`、`证据齐全`、`验证成立` | 实际有哪些证据？ |
| `落盘` | `存档`、`写入指定文件并保存` | 保存了什么、保存在哪里？ |
| `闭合` | `信息完善`、`调用链已完整追踪`、`验证证据齐全` | 到底完成了什么？ |
| `颗粒度` | `逐行修改`、`逐函数核对` | 对象和尺度是什么？ |
| `锚定` | `以……为准`、`引用……的定义` | 是采用规范、引用还是复制？ |
| `拍板` | `选择`、`决定` | 作出了哪项决定？ |
| `搞定` | `完成具体修改`、`通过具体测试` | 完成对象是什么？ |
| `跑通` | `完成某流程的端到端测试，结果为……` | 是成功运行还是测试通过？ |
| `兜底` | `备用`、`失败时的回退处理` | 指备用方案还是异常处理？ |
| `拷贝` | `复制` | 不改变已有技术词义。 |
| `补齐` | `补充` | 补充的内容是什么？ |
| `落地` | `部署`、`实施` | 实际执行了什么？ |
| `锚点` | `创建标签`（当动作确为创建标签时） | 不要把引用位置误写成 Git 标签。 |

表中词语不是一律禁止的字符串。若特定术语具有明确技术定义，应保留：如“拷贝构造函数”“内存拷贝”；在存储系统中，“落盘”若准确指缓冲数据持久化到介质，也可以照用。

### 5.3 不以修辞代替事实

读者应该能明确判断：

- 验证全部完成还是只覆盖一部分。
- 一段话是观察结果、结论、推测还是下一步计划。
- “完成”指代码修改、文件保存、部署执行还是验证通过。
- 某内容被引用、复制、作为规范依据，还是仅用于对照。

## 六、引用与转述

口语化的用户原话进入工程记录时，按原意转成事实性描述，不替用户改变立场、程度或证据强度。

| 原话 | 在对应事实成立时的文档表述 |
| --- | --- |
| `垃圾` | `未验证内容`（仅当确实指缺乏验证） |
| `糊弄` | `未按规范执行的行为`（仅当已有证据） |
| `快挖完了` | `自认为接近完成` |

不能将“快挖完了”改为“已经完成”，也不能将用户的主观评价写成客观定论。

函数名、类名、变量名、代码、命令、文件路径、错误码、协议字段、日志、commit hash、第三方引用及用户要求保持原样的内容必须精确保留。需要解释时，在原文之外补充说明。

## 七、按产出类型执行

### 7.1 Git commit message

提交主题说明**改动动作和具体对象**。按仓库惯例使用 `feat:`、`fix:`、`docs:` 等前缀时，前缀不代替实质内容。

不合格：

```text
fix: 修复问题
```

合格：

```text
fix: 修复令牌过期后刷新请求失败的问题
```

复杂提交可以在正文记录背景、主要改动和确实执行的验证。提交前确认消息与实际 diff 相符，不把实验日志全部塞进主题。

### 7.2 PR 标题、描述和代码审查记录

- 标题说明修改目标和对象，不写“优化”“更新”而不补充范围。
- 描述说明关键变更、相关影响及可核验的验证范围。
- 审查意见指出具体文件、行为、条件和后果；避免只有“这里有问题”。
- 不把推测写成已复现的错误；能定位时附准确位置或复现条件。

### 7.3 项目文档、工作日志和测试报告

记录应当脱离聊天上下文也能理解。必要时写明目标、实际改动、执行方式、观察结果和遗留问题。

不合格：

> 阶段 B 完成。T3 通过。之后继续收尾。

合格：

> 已将服务端工具配置与客户端工具列表分离。验证 3 检查调整后的工具列表，响应中仅包含客户端声明的工具。尚未验证多轮会话中的兼容性。

测试结论应与执行记录一致，不能使用某一项测试的成功代替整个模块的验证结论。

### 7.4 `AGENTS.md`、`SKILL.md` 和其他 Agent 交接材料

对未来执行任务的 Agent，至少明确与该任务相关的：

- 生效场景及触发条件。
- 必须执行的具体动作。
- 涉及的文件、信息与操作范围。
- 既有仓库约定、必须保留的技术标识符及例外情况。
- 可观察的完成条件与尚未解决的事项。

交接内容重点保存**事实、决策依据、关键路径、当前状态和下一步**。不要堆积仅在当前对话可理解的代号或口头承诺。

不为了显得正式而增加未定义缩写、空洞原则或复杂登记体系。

### 7.5 Hook、脚本和 CI 的提示文案

持久化在脚本、配置或源码中的用户可见错误消息，尽量指出失败操作、失败对象和可用诊断信息；能给出明确修复办法时再补充。

不合格：

```text
检查失败，请处理。
```

合格：

```text
提交消息检查失败：主题没有说明具体修改对象。请将“修复问题”改为描述本次修复内容的句子。
```

不得编造退出码、原因或结果；不得破坏脚本原有 stdout/stderr 约定、机器可解析格式或控制流程。

### 7.6 代码注释和程序文案

仅审查任务实际涉及的新写或修改文字，不为清理措辞而遍历并改写整个代码库。

- 注释解释必要的原因、约束或非显而易见的行为，避免只是复述代码。
- 面向用户的提示要指出可操作的问题，不用空洞的“发生错误”。
- 固定协议字符串、测试快照、国际化键、外部接口约定不得因语言偏好而更改。

## 八、写入前的检查流程

### 8.1 确定事实与项目约定

1. 确认将修改的文档、提交消息或提示文案及其目标读者。
2. 确定真实执行的动作，区分计划、已修改、已验证与未验证。
3. 查看相关项目术语、提交惯例和编号体系，优先复用现有约定。
4. 如需长期代号，先定义含义，再按现有单一权威位置登记。

### 8.2 起草与改写

1. 标题、编号和名称使用具体对象与动作。
2. 重要结论写明实际检查范围、观察结果与未覆盖部分。
3. 使用平实中文和具有确定定义的专业术语。
4. 不以比喻、口语、网络词汇或夸张程度词代替事实。
5. 精确保留代码、命令、路径、错误码及原始引用。

### 8.3 最终检查

- [ ] 标题、提交主题和编号项能否单独看懂？
- [ ] 是否出现未定义的 `T3`、`S2`、`阶段 A` 等代号？
- [ ] 新的长期代号是否按现有约定定义或登记？
- [ ] 是否用“钉死”“落盘”“闭合”“拍板”“搞定”等词遮蔽动作或结果？
- [ ] 重要结论是否写清验证对象、范围和观察到的事实？
- [ ] 是否区分计划、推测、用户判断、已修改和已验证？
- [ ] 是否把未运行的测试写成通过，或把局部成功扩大为全局成功？
- [ ] 用户口语是否在不改变原意和事实强度的前提下准确转述？
- [ ] 是否误改了技术标识符、路径、API 字段、命令、原始日志或引用？
- [ ] 文档及交接记录是否无需依赖当前聊天即可理解？
- [ ] 是否存在无必要的 emoji、装饰符号或空洞修辞？

发现问题时直接修改目标文字，不生成无关的自检声明。

## 九、执行边界

1. **不擅自重命名代码标识符。** 此规范是文字质量要求，不授权变更 API、函数、变量、数据库字段或外部协议。
2. **不机械套用禁词表。** 具有明确、可核查的学科或工程含义时可以保留原词。
3. **不制造验证证据。** 文案修订不能代替测试，也不能把计划写成执行结果。
4. **不制造额外工作。** 简单条目可以直接写清楚；没有登记机制时不为一次性编号创建机制。
5. **不改写必须保留的原文。** 对日志、命令、原始错误消息、引用与技术标识符，保持准确。
6. **遵守现有仓库约定。** 保留既有命名和专业术语，必要时补充解释。
7. **只处理当前任务相关的持久化文本。** 不因本 Skill 激活而主动扫描、改写或统一全仓库文风。
8. **本 Skill 是表达规范，不是强制门禁。** 如需自动拒绝不合规的提交，另使用确定性的 Git Hook 或 CI 校验。

最终目标是让长期保存的文字真实、清晰、可追溯，而不是让它们更长或更像模板。
