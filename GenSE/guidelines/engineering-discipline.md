# 工程执行与行为准则

## 一、适用范围与目标

本准则适用于 Agent 在软件开发、架构设计、代码重构、缺陷修复、测试验证及工程文档维护中的执行行为，旨在消除自动化编码常见的六类系统性偏差：**跨阶段越界执行、过度设计、过度防御、重表面结果轻结构质量、无差别全量测试、以及将过程记录混入正式文档**。

---

## 二、步幅控制：结合任务授权与实际影响推进

1. **区分“方案探讨”与“执行指令”**
   - 当用户阐述后续规划、探讨模块实现先后顺序或征询可行性时，提供结构化分析与分步建议；当用户仅下达单一前置指令（如创建分支、初始化目录结构、仅整理文档）时，精准完成该项操作并等待下一步指令。
2. **按需设置关键确认点（Checkpoints）**
   - 需求、架构、公共契约与前端原型是检查目标和方案是否一致的关键节点，不要求每经过一个阶段都重新获得确认。结合用户当次指令、已确认决策与变更影响判断是否需要停靠，遵守用户明确指定的评审点。
   - 用户已授权完整实施、方向与边界清楚时，可连续推进范围内的设计、实现与验证；常规实现细节采用合理方案，不重复询问已有授权。
   - 出现影响目标或范围的实质性歧义、尚未授权的重大架构或公共契约取舍、范围扩展或不可逆操作时，先说明问题与建议并确认；不依赖该决策的已授权工作可继续推进。
   - 对体验方向尚不明确的前后端联动探索，优先用轻量前端原型获取反馈；交互要求已明确或已有可沿用方案时，可直接完成联动实现与验证。
3. **收敛单次变更范围**
   - 每次仅修改当前任务授权范围内的模块与文件，保持无关模块、未授权的 Git 提交与分支合并处于静止状态。

---

## 三、设计克制：匹配项目定位，消除偶然复杂性

根据项目的实际规模、生命周期与非功能需求进行架构与数据建模，保持设计精炼直接：

1. **以最简模型承载已确认需求**
   - 根据业务不变量、并发一致性与追溯要求决定数据粒度；聚合计数能完整满足需求时保持简洁，需要逐笔生命周期、归属或补偿依据时保留明细记录。
   - 根据审计语义、查询与保留要求决定复用通用日志还是建立专门历史记录，不仅依据前端是否展示作取舍。
   - 根据数据量、查询时效与性能需求选择实时聚合或汇总模型，避免为假想需求预建冗余结构。
   - 根据外部依赖的交付保证、失败恢复时效与运维成本选择重试或补偿方案，复杂度与实际可靠性要求匹配。
2. **仅在真实边界处建立抽象**
   - 围绕真实的模块边界或可替换契约定义接口，内部辅助类与工具函数保持直接具体。
   - 严格遵循架构选型确定的技术范围，保持构建脚本与容器编排简洁直观。
3. **优先沿用生态默认配置**
   - 当操作系统、语言运行时、框架与数据库的默认配置已满足业务需求（如默认本地时区、默认时间序列化、默认连接池参数）时，直接沿用默认行为。
   - 既有项目以仓库声明的版本与兼容性约束为基线；新建工程或获准升级依赖时，查询官方支持状态与兼容要求，选用当前受支持的稳定版本，并在项目配置中明确版本。Skill 中的版本示例不作为永久默认选型。

## 四、防御克制：依托框架标准机制，避免重复造轮子

充分信任语言运行时与成熟框架的内置能力，保持基础设施层薄而清晰：

1. **优先复用已选框架与组件的标准能力**
   - 参数校验、JSON 序列化/反序列化、字段映射、内容协商、分页与基础 CRUD，优先使用所选框架与组件的标准机制（如声明式校验注解/Schema、ORM 内置方法、UI 标准组件）；组件库是否引入及使用范围由项目需求决定。
   - 直接复用框架提供的校验异常结构提取错误详情，避免自行编写复杂的反射解析或嵌套路径遍历逻辑。
2. **保持异常处理层次扁平**
   - 通过单一的顶层全局异常处理器与必要的认证/授权响应入口实现统一错误返回，省去针对非生产极端故障的多层异常捕获与底层容器错误路由接管。

---

## 五、质量内建：同步保障功能实现与代码结构质量

将工程规范贯穿于编码过程之中，确保交付代码兼具功能正确性与结构可维护性：

1. **严格落实分层职责与类型安全**
   - 业务逻辑内聚在领域/业务服务层，协议适配层与根视图组件保持轻量；
   - 状态、角色、类型、错误码等有限业务取值全面采用强类型枚举或字面量类型；
   - 查询构建器与显式 SQL 按复杂度合理分工，保持业务方法短小可读。
2. **实质性落地技术选型与重构目标**
   - 架构选定引入某项框架或组件库（如 ORM、安全框架、UI 组件库）后，在业务代码中切实接入并替代原生低层实现。
   - 重构须落实到代码职责边界与运行行为的实质改善，而非仅调整命名或目录位置。
3. **交付前执行代码质量自检**
   - 功能编码完成后，主动核查并消除硬编码常量、跨模块直接写表、职责越界或冗余配置，再提交人类验收。

---

## 六、验证分层：按改动粒度与风险级别匹配测试策略

建立分层的验证体系，兼顾反馈速度与验证深度，避免在每次微小改动后无差别执行全量重型测试，也不追求脱离风险比例的机械测试完备度：

1. **按改动性质选择验证层级**
   - **文档修订、默认配置精简或纯静态文案/样式微调**：直接核对变更内容，无需触发构建或运行测试套件。
   - **日常小步编码与局部逻辑调整**：优先执行快速的**静态分析、类型检查、语法/增量编译检查**（如 TypeScript 类型检查、Linter、增量编译），或仅运行当前关联的单个单元测试。
   - **功能切片完成与关键里程碑**：在完成完整功能切片、合并并行子代理分支，或修改数据库事务、并发控制、权限拦截等核心逻辑时，集中执行集成测试与真实数据库验证。
2. **测试覆盖与业务风险成比例**
   - 将测试重心放在高风险的核心业务不变量（如状态机合法迁移、并发下的资源扣减与释放守恒、越权访问拦截）上。
   - 常规简单 CRUD、纯视图映射与低风险辅助逻辑依托类型系统与静态检查保障，保持测试套件精炼高效。
3. **以根因诊断驱动修复**
   - 验证失败时，先分析定位根因（代码逻辑缺陷、测试前置假设偏差、环境配置问题或规格冲突），针对根因修复，保持业务断言与约束条件的严谨性。

---

## 七、文档纯粹性：隔离设计规格与过程记录

保持正式工程文档的专业性与长期可维护性，将设计结论与开发过程记录严格分离：

1. **正式文档仅呈现当前有效的客观规格**
   - `srs.md`、`architecture.md`、数据模型设计与部署文档应保持成品级质量，仅陈述系统**当前有效的业务规则、架构结构与技术方案**。
2. **将过程性信息移出正式设计文档**
   - **分离进度与待办**：开发进度、已完成/未完成模块清单统一通过 Git 提交记录、Issue 或独立的阶段评估记录管理，不写入架构或数据模型设计文档。
   - **分离本地调试细节**：架构文档聚焦系统级组件关系与边界，不掺杂本地开发配置文件名、临时调试开关或框架内部实现细节。
   - **采用直接的肯定表述**：设计方案变更或精简后，直接更新为最新方案的正面描述，省去对旧方案的删减说明、自我解释或冗余的否定句。
3. **及时清理临时工程产物**
   - 阶段性代码评估草稿、辅助工具生成的本地隐藏目录、已合并的 `git worktree`、不再需要的 `.gitkeep` 占位文件及临时构建产物，在阶段收尾时及时清理归档。
