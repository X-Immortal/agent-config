# 通用前端工程、UI/UX 交互与演示数据细则

本规范提炼跨前端框架（适用于 Vue、React、Svelte、Next.js 等）的通用前端工程与交互设计准则。状态所有权、交互一致性、视觉层级与可访问性是通用要求；组件、导航、反馈和检索形态应根据产品类型、平台习惯与项目约定选择，下述方案不要求全部采用。

## 1. 视图架构与组件生态

1. **按角色端面与功能域组织工程**
   - 按功能模块组织视图（Views/Pages）、导航配置与网络请求模块；当不同角色界面的访问边界或布局明显不同时，可使用独立布局容器（Layout）与路由子树隔离，结构相近时复用公共布局。
   - 将状态划分为组件局部状态与必要的全局共享状态（如当前认证会话、全局共享摘要），保持状态流向清晰。
2. **复用合适的组件并保持主题一致**
   - 优先复用项目已有设计系统或成熟组件处理复杂交互；原生控件能满足需求时可直接使用，按产品形态、维护成本与设计要求决定是否采用组件库及其范围。
   - 通过项目既有设计令牌（Design Tokens / CSS 变量）或样式机制管理主题色、圆角与字体层级；原生、自定义或库组件均应满足键盘操作、焦点可见、语义标签与对比度要求。
3. **按交互不确定性使用原型**
   - 当界面布局或检索体验尚未明确，且会影响后端接口与数据模型时，先用轻量原型验证关键交互；要求已明确或已有可沿用设计时，可直接联动实现。是否停靠确认结合授权与变更影响判断。

## 2. 页面流转、导航与反馈机制

1. **按访问与流程需求选择视图形态**
   - 需要直接访问、分享或独立导航的完整内容适合独立路由；短操作或需保留上下文的流程可采用弹层、侧栏或内嵌视图，并遵循目标平台的导航习惯。
2. **一致的操作文案与认证引导**
   - 受保护操作清楚表达业务动作与登录要求；按产品流程选择点击后引导登录、提前说明或禁用并解释原因，认证后在适用时恢复用户原操作上下文。
3. **符合导航语义的返回与精简导航层级**
   - “返回”操作与文案及导航语义一致：需回到上一访问位置时使用可用的应用内历史；需回到父级或列表时使用明确目标，处理直接打开页面时缺少前置历史的情况。
   - 当顶部导航栏已清晰高亮当前所在板块时，页面内容区直接切入核心内容，保持标题与导航层级精简。
4. **按影响范围选择结果反馈**
   - 字段错误优先就近展示，短暂且无需后续操作的结果可使用 Toast / Message；需持续查看或采取行动的信息使用持久提示或通知区域。位置与样式遵循项目约定，避免关键错误仅靠短暂浮层传达。

## 3. 信息层级、列表检索与微观交互（适用于含列表/目录的界面）

1. **列表卡片与详情视图的信息密度分层**
   - 列表卡片聚焦于辅助用户快速浏览与筛选的核心摘要（如封面、标题、核心价格/数值、可用状态与关键简短标签），将长文本简介与次要属性留给详情页，保证单屏浏览效率与呼吸感。
2. **清晰的状态视觉反差与交互态势**
   - 可用、不可用与禁用状态用清晰的文字、标签及视觉差异表达，不仅依赖颜色区分。
   - 悬停与焦点反馈反映实际可执行的操作；资源不可用但仍可查看详情时，保留查看入口的交互反馈，真正禁用的控件清楚说明原因。
3. **高效主次分明的检索工具栏**
   - **按查询成本选择触发方式**：响应快、成本低的检索可实时触发并对连续输入防抖；高成本查询或需一次组合多个条件时，可显式提交。异步结果应与当前已提交条件对应，避免旧请求覆盖新结果。
   - **按频率与空间组织条件**：高频条件优先可见，低频或多维条件按需折叠；保留已选条件的可见反馈，不固定工具栏的控件组合。
   - **控件形态贴合数据特征**：按选项数量、离散或连续特性选择标签、选择器或区间输入；排序选项覆盖实际任务需要，避免为形式对称增加无意义选项。
4. **同组控件视觉与动效统一**
   - 同一工具栏或表单区内的输入框、下拉框与按钮保持统一的边框粗细、圆角、Focus/Hover 状态色、箭头翻转及下拉展开过渡动画。
   - 轮播控制、返回顶部等辅助控件按目标平台、阅读方向与设备选择位置，提供可理解的标签以及相应的焦点、触摸或悬停反馈。

## 4. 视觉协调、文案克制与标杆推广

1. **色彩与版面服务于信息层级**
   - 页面背景、内容容器与强调色遵循项目视觉方向，保持层级可辨与对比度可读；色温、装饰强度与留白随产品定位决定。
2. **流畅的叙事型展示（适用于品牌/规则介绍首页）**
   - 包含多段核心价值或流程介绍的首页，按阅读顺序组织板块与过渡，兼顾不同视口尺寸及减少动态效果的偏好；无需固定为整屏板块或特定左右布局。
3. **简洁克制的产品级文案**
   - 标题、表单与说明文字使用自然、准确的产品语言，省去生硬的口号式修饰小字与多余标点，保持必填标识（`*`）等表单细节完整。
4. **先树标杆页面，再全站推广对齐**
   - 需要统一多页面风格时，先选择能代表项目主要交互的一两个视图验证设计，再复用到其余页面；已有设计系统时直接沿用，只有方向未决或用户要求评审时才停靠确认。

## 5. 按需准备有代表性的演示数据（Seed Data）

- 需要开发或演示数据时，按任务选择初始化注入、显式执行种子脚本、固定夹具或 Mock；自动注入应限于明确的开发或演示环境，避免覆盖已有数据。
- 数据名称、媒体比例与数值分布应符合领域特征，并覆盖典型、空白与边界状态；可使用合理虚构数据，无需依赖真实个人信息。需要可复现验证时保持数据稳定。
