# 通用后端工程与代码组织细则

本规范提炼跨编程语言（适用于 Go、Node.js/TypeScript、Python、Java、Rust 等）的通用后端工程原则，涵盖模块边界、关注点分离、领域类型、数据持久化与并发一致性。

## 1. 模块边界与关注点分离

1. **按业务领域内聚组织代码**
   - 顶层按高内聚的业务领域划分模块（辅以公共配置与基础设施模块），使目录结构直接反映业务能力。
   - 模块内部目录层级保持扁平直观：文件数量较少时直接置于模块根部；同类实现文件较多时再按职责归纳子目录。全局配置统一收敛在配置目录中。
2. **清晰的职责分层与单向依赖**
   - 将后端代码划分为职责清晰的单向协作层次：
     - **协议适配层（Handler / Controller / Router）**：负责解析请求参数、触发输入校验、调用业务层并映射为标准协议响应。
     - **领域与业务逻辑层（Service / UseCase / Domain）**：内聚核心业务规则、状态流转校验与事务编排，保持与底层传输协议上下文解耦。
     - **数据访问与基础设施层（Repository / Store / Mapper / Client）**：封装数据库读写与外部服务调用细节。
   - **跨模块通过公开契约协作**：每个业务模块对自身管理的数据表拥有唯一写入权；跨模块交互通过对方公开的业务函数或接口完成，保持模块间单向依赖。
   - 按真实的业务边界与解耦需求定义抽象接口，保持代码结构轻盈直接。

## 2. 强类型领域常量与错误码

1. **使用类型安全机制表达有限集合**
   - 业务状态、角色类型、操作类别、执行结果、排序维度、筛选区间与业务错误码等有限取值集合，统一使用语言原生的强类型枚举、联合字面量类型（Union Types）或具名常量类型定义，贯穿数据模型、业务逻辑与接口契约。
   - 在数据库持久化与 JSON 等序列化边界使用稳定、可读的语义化编码。
2. **内聚枚举伴随语义**
   - 按业务模块就近组织领域枚举，公共枚举置于公共模块；直接利用枚举标识符或简洁编码表达语义。
   - 将与错误码强关联的元数据（如对应的 HTTP/RPC 状态码、默认错误分类）内聚在同一定义处，简化顶层错误映射逻辑。

## 3. 数据访问、事务与并发一致性

1. **发挥数据访问库标准能力，合理结合显式查询**
   - 常规单表增删改查、简单动态过滤与分页查询，直接使用 ORM 或查询构建器（Query Builder）的标准方法，保持代码简洁。
   - 涉及复杂多表关联统计、特定行级锁或高并发原子条件更新时，在数据访问层编写显式 SQL 或原子操作语句，兼顾业务层可读性与执行效率。
2. **保证本地事务与并发安全**
   - 同一业务动作引起的核心状态变更、资源增减、资金记录与审计日志写入，在同一数据库事务中原子提交。
   - 并发修改共享资源时，使用原子条件更新（如在 `UPDATE` 条件中校验预期前置状态与余量，并检查受影响行数）、唯一约束或按固定主键顺序加锁，确保并发场景下的数据不变量成立。
3. **隔离外部网络 I/O 与明确部分成功语义**
   - 将邮件、短信、Webhook 等外部网络调用置于数据库锁与核心事务边界之外。
   - 当主业务事务已成功提交、仅后置非阻塞动作发生异常时，接口语义应准确表达主业务已生效，避免调用方误判整体失败并重复执行；后续状态通过响应字段、查询接口或异步通知表达，按既有契约与一致性要求选择，不预设特殊状态码。

## 4. 声明式输入校验与精简错误处理

1. **采用声明式输入校验**
   - 使用语言生态成熟的声明式 Schema 或校验器（如 Zod、Pydantic、Validator 标签/注解）在接口入口层完成字段必填、类型、范围及集合元素唯一性校验，让业务层专注于领域规则。
2. **保持错误处理与日志组件精简独立**
   - 通过单一、清晰的顶层全局错误处理中间件/拦截器，将业务异常、认证授权异常与输入校验异常转换为统一的错误响应结构。
   - 审计与业务操作日志的持久化封装为独立的内部服务组件，在业务流转中显式调用，与协议层响应格式化逻辑保持解耦。
