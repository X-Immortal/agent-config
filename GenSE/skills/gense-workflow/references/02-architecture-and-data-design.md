# 阶段流程二：系统架构与适度详细设计

本流程适用于需求规格明确后的系统架构设计、模块边界划分、核心数据建模及一致性机制设计，独立于具体编程语言与框架。

## 1. 设计重心：安放本质复杂性，减少偶然复杂性

架构设计的目标是回答三个核心问题：**哪些核心规则必须集中维护？哪些数据归哪个模块唯一管理？当需求变化时会影响哪些边界？**

1. **单一架构主文档 + 按需专题设计**
   - 默认由 `docs/architecture.md` 集中记录影响多个功能或后续演化的架构决策（架构风格、技术选型、模块职责与单向依赖、核心业务流程、关键数据模型与一致性边界、显式排除的复杂方案及 `ADR`）。
   - **按需展开详细设计**：仅当某个复杂专题（如高并发事务锁顺序、复杂的公共错误契约）无法在 `architecture.md` 中简明表达且需要跨多个开发任务长期引用时，才拆出如 `docs/design/` 下的独立专题文档。普通函数拆分、工具类与常规 CRUD 由编码阶段直接确定。
2. **避免文档与代码的双重维护负担**
   - **数据库设计重在关系与机制**：文档聚焦于核心实体关系（ER 图）、表归属、业务不变量及关键并发/幂等机制；完整字段类型、索引细节和 DDL 最终以仓库中的实际 Schema 初始化脚本（或迁移脚本）为权威来源，避免在 Markdown 中重复抄写全量表结构导致后续修改脱节。
   - **API 默认采用 Code-First**：设计阶段先明确接口风格、认证方式、统一响应外层结构、公共错误码及关键操作语义；具体接口定义在代码实现后直接导出为 OpenAPI 规范（如 `openapi.yaml`）并核验，无需预先手写完整接口 Markdown 清单（仅在跨独立团队协作等确有必要时采用 API-First）。

## 2. 总体架构、选型与模块边界

1. **务实的技术选型与负向边界（ADR）**
   - 选择与项目规模、团队及交付目标匹配的架构风格，汇总各端/各层技术选型及具体职责，使用 Mermaid 或 SVG 绘制系统总体拓扑图。
   - 明确记录当前阶段**不采用**的复杂组件或机制，并对重大技术取舍保留简短 `ADR`（背景、选项、决定、理由与影响）。
   - 组件与机制的引入或排除应依据部署规模、数据演进、可靠性与运维需求，不直接复用其他项目的取舍清单。
2. **高内聚模块划分与数据所有权（Data Ownership）**
   - 依据业务领域划分模块，使用 Mermaid 绘制模块单向依赖图。
   - 明确每个模块的公开边界与**唯一数据写入权**：各模块负责维护自身的数据表，跨模块协作通过对方公开的业务接口完成。
   - 明确认证授权、定时调度、外部通知等基础设施与业务模块的调用方向，确保业务规则集中在业务模块内部。

## 3. 核心数据模型、事务与并发一致性

当系统涉及持久化与多状态流转时，将设计精力集中在决定数据正确性的关键机制上：

1. **精炼的数据建模取舍**
   - 在满足当前业务规则、并发安全与审计追溯的前提下，选择最简充分的数据模型，不为假想需求预留冗余表。
   - 按业务不变量与追溯粒度判断聚合计数是否足够；需要逐笔占用生命周期、归属或补偿依据时保留明细。历史记录是否复用通用日志，取决于审计语义、查询与保留要求。
2. **事务边界与并发控制约定**
   - 明确哪些状态变更、资源增减、资金记录与审计日志必须在同一本地事务中原子提交。
   - 对共享资源并发争抢（如余量扣减、总额调整与新建单并发），明确约定**原子条件更新规则、跨操作统一的加锁顺序（如多资源按主键升序操作防死锁）及唯一约束职责**。
   - 明确异常回滚边界，确保需要持久化的拒绝/取消状态不会被异常一并回滚。
3. **幂等机制与外部 I/O 隔离**
   - **多步提交的一致性语义**：明确提交按用户确认时的数据还是最新有效数据执行，并规定中途变化的处理方式；按需选择快照绑定、版本校验或提交时重校验，幂等标识与选定语义保持一致。
   - **状态变更幂等**：重复触发支付、取消、履约、退回等请求时保持首次已生效结果，避免重复扣减/释放资源或重复记录成功日志。
   - **外部调用移出事务**：将邮件、短信、第三方 HTTP 调用置于数据库事务与锁持有期之外；根据交付保证、恢复时效与运维能力选择重试或补偿机制，避免默认依赖人工处理或引入超出需求的机制。
