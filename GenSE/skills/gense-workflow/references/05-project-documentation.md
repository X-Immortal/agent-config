# 项目文档目录结构、单一权威来源与图表规范

本文件规范项目级文档目录的轻量化组织、各信息维度的单一权威来源边界、Code-First 接口契约导出与图表绘制准则。

## 1. 轻量化文档结构与单一权威来源

**用文档帮助下一轮开发恢复上下文与判断，而非用文档展示工作量。** 推荐的默认项目文档结构如下（仅创建项目实际用到的文件）：

```text
project/
├── AGENTS.md                  # 项目入口、工程约束、运行/验证命令与文档导航
├── docs/
│   ├── srs.md                 # 需求与验收条件的权威来源
│   ├── architecture.md        # 总体架构、模块边界、数据归属与关键技术决策（ADR）
│   ├── design/                # 可选：仅当并发事务、公共响应契约等需独立专题时创建
│   └── open-questions.md      # 可选：需求/设计阶段的待决问题与 DEC 决策索引
├── deploy/                    # 数据库初始化 Schema 脚本、种子数据、部署配置
└── ...                        # 源码、测试与自动导出的接口规范（如 openapi.yaml）
```

各类信息保持**单一权威来源（Single Source of Truth）**，各司其职：

| 信息维度 | 权威载体 | 内容边界 |
| :--- | :--- | :--- |
| **业务行为与验收判据** | `srs.md` | 业务目标、角色权限、功能/非功能需求、业务规则与可验证验收条件 |
| **系统结构与技术取舍** | `architecture.md` 及可选专题设计 | 架构风格、选型职责、模块单向依赖、核心协作流程、并发/事务边界、部署拓扑与 `ADR` |
| **实际数据库结构** | `deploy/schema.sql`（或迁移脚本） | 完整字段定义、索引与约束（设计文档聚焦实体关系与并发机制，不重复抄写全量 DDL） |
| **实际 API 契约** | 代码及自动导出的 `openapi.yaml` | 具体接口路径、请求/响应字段与校验规则（设计阶段仅约定统一外层响应与错误码契约） |
| **项目进度与验证事实** | Git 提交历史、Issue 或独立评估记录 | 已完成工作、测试验证结果与待办事项（与架构和数据库设计文档保持分离） |

## 2. Code-First 接口契约导出

- 当技术栈支持从代码注解、Schema 或类型定义生成接口文档（如 OpenAPI、TypeDoc、Protobuf）时，采用 **Code-First** 方式：在接口实现后直接从代码导出单一格式的权威契约文件（优先保留 `openapi.yaml`），并验证生成结果的完整性。
- 仅在跨独立团队并行开发等确需契约先行的场景下才预先编写接口清单。

## 3. 增量维护、版本演进与历史状态标记

1. **精准增量更新并同步版本号**
   - 当需求、架构或数据模型发生实质变化时，只精准更新**受影响的**文档章节、图表（ER 图、流程图）与关联引用，并同步递增文档版本号与修订日期。
2. **清晰标记历史方案状态**
   - 曾经讨论或使用过、但后续被替代的旧方案，在决策记录中明确标记为“已替代/已停用”，并在正文中清理旧模型残留；阶段收尾时归档核心文档并清理临时过程性记录。

## 4. 图表与极简表达规范

1. **使用结构化矢量图表**
   - 系统拓扑图、模块依赖图、状态机、时序图与数据库 ER 图优先使用 **Mermaid 或 SVG** 绘制，保持直观清晰。
2. **使用直接、精炼的肯定句式**
   - 直接陈述系统“采用什么方案、遵循什么规则”，行文紧凑、可核验。
   - 对于直接沿用语言、操作系统或框架默认行为的约定（如统一采用单一标准时区、使用默认时间序列化格式），用一两句话直接写明结论。
