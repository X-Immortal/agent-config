# 阶段流程三：增量实施与分层验证反馈

本流程适用于架构与关键设计明确后的编码实现、端到端切片交付及分层验证与反馈迭代阶段，独立于具体编程语言与技术栈。

## 1. 结合“最小公共底座”与“端到端功能切片”推进实现

避免“先孤立地铺完全部后端所有模块、最后再一次性对接前端”导致的契约脱节与返工，采用**最小底座 + 端到端功能切片（Feature Slicing）**的方式推进：

1. **第一步：搭建最小必要的公共底座**
   - 建立工作分支与清晰的模块目录骨架。
   - 落地统一响应结构、全局错误处理底座、核心数据库初始化脚本及认证会话基础能力。
2. **第二步：按可运行、可观察的业务切片推进**
   - 围绕核心业务流程，优先打通端到端（数据层 ↔ 业务层 ↔ 接口层 ↔ 前端视图）可运行切片，尽早通过实际运行观察界面展示、筛选排序、字段完整性与状态流转。
   - 对体验方向尚不明确的功能（如列表检索、多维筛选、页面布局），可先用前端原型获取反馈；要求已明确时直接联动实现，并尽早结合实际视图验证字段、交互与接口契约，减少后期返工。
3. **第三步：稳态契约下的模块并行扩展**
   - 当各模块的领域模型与接口边界已经清晰稳定、且多个待开发模块互不依赖时，可按模块并行推进开发（详见 `04-project-git-and-parallel-agents.md`），每完成一个清晰的逻辑单元即验证并提交版本。

---

## 2. 分层验证、根因诊断与反馈循环（Feedback Loop）

根据当前改动粒度与业务风险**分层匹配验证手段**，兼顾日常反馈效率与关键节点的验证深度，避免脱离风险比例盲目追求测试完备性：

1. **验证金字塔与时机分层**
   - **纯文档、配置精简或静态文案/样式微调**：直接核对内容，无需触发构建或运行测试套件。
   - **日常小步开发与局部改动**：优先运行极速的**静态检查、类型检查或增量编译检查**（如 TypeScript 类型检查、代码编译、Linter），或仅单跑当前改动的单个测试方法。
   - **阶段里程碑与核心流转集中验证**：在完成一个完整功能切片、子代理合并集成，或修改了数据库事务、并发扣减、权限控制等高风险逻辑时，集中执行真实数据库集成测试与端到端流程验证。
   - **按风险聚焦测试重点**：测试用例重点覆盖核心业务不变量（如状态机合法迁移、并发下的余量与占用量守恒、越权阻断），不为简单样板代码编写冗余的测试矩阵。
2. **根因诊断与规格/实现双向修正**
   - 验证失败时，先诊断根因属于**代码实现缺陷、测试假设错误、运行环境问题还是需求规格冲突**，定位根因后修正，保持业务约束与测试断言的真实性。
   - 将运行观察与用户反馈对照 SRS：若发现规格不完整或架构需调整，遵循 `明确问题 → 给出最小调整建议 → 按决策更新规格/设计 → 完成代码修正`。
3. **外部配额保护**
   - 本地运行与自动化测试中，对邮件、短信、支付等消耗真实配额或产生外部副作用的第三方接口统一使用模拟（Mock/Stub）实现隔离。
